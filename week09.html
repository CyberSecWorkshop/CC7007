AsyncRAT in ANY.RUN
Archive Delivery & Config-Based C2

An encrypted ZIP archive opened in WinRAR. A fake installer executed manually by the user. A .NET AsyncRAT payload that profiles the host and reveals its real command-and-control details through configuration extraction, malicious DNS resolution, and a direct connection on port 2000. This workshop uses ANY.RUN's interactive sandbox to analyse the actual public task. You will read the Process Tree, inspect process details, review DNS and network noise, and use the malware configuration view together with the connections panel to derive the real C2 from the evidence.

Tool: ANY.RUN Sandbox (2026)
OS: Windows 10 x64 VM
Platform: Browser — any.run
Sample: ZIP → WinRAR → EXE
Skill: Noise filtering · Config extraction · Host connection proof
🧠 WHAT ARE WE ACTUALLY DOING? — READ FIRST

This AsyncRAT task is different from the fictional injection-heavy scenario often used in demos. Here, the malware arrives as an AES-encrypted ZIP archive, is opened through WinRAR, and the payload is executed directly by the user from the Desktop. The main analytical challenge is still separating real indicators from system noise, because much of the visible HTTP traffic belongs to legitimate Microsoft and DigiCert services. But the current ANY.RUN view gives you more than config alone: the real C2 is supported by malware configuration extraction, a DuckDNS domain, a malicious DNS resolution, and a direct connection from PID 7660 to 192.169.69.26:2000.

⚠️ Important scope note

This workshop now matches the actual ANY.RUN task as currently shown. Do not claim phishing, Outlook, script chains, injected processes, Startup-folder persistence, or hollowing unless the task itself shows them. But do not understate the network evidence either: page 2 now shows a malicious connection and malicious DNS entry for donzola.duckdns.org.

What new ANY.RUN skills does this add?

Archive-delivery tracing
Use the Process Tree, file activity, and WinRAR command line to prove that the payload came from an AES-encrypted ZIP archive and was executed manually after extraction.
Noise filtering
Distinguish Windows telemetry, DigiCert OCSP, Microsoft update traffic, and login endpoints from actual malware infrastructure. You need both restraint and precision here.
Config + connection correlation
Use MalConf to extract the AsyncRAT C2 domain, port, mutex, version, and install folder, then validate that against DNS and the connections panel.
Contextual .NET confirmation
Use process modules such as mscoree.dll to confirm the payload is managed code, supporting AsyncRAT attribution without inventing injection evidence.

📁 THE CASE — READ BEFORE ANYTHING ELSE
// Case Reference: ASYNCRAT-ANYRUN-09 · Task: b7ff470d-5740-43b6-80ae-376d93c54b4d · OS: Windows 10 x64

A suspicious archive named 1f3c7379dd29298aa24b3aa3a3113ed3051f4515bc3c016893e285d311a74202.zip was detonated in ANY.RUN. The archive is AES-encrypted and contains a single executable with a long hash-like name. The user opens the archive through WinRAR, extracts the payload to the Desktop, and executes it manually.

ANY.RUN detects the sample as AsyncRAT via both YARA and mutex artefacts. The payload presents itself as Maxthon Installer, but its filename, context, and behaviour make clear that it is not a legitimate installer. The process then performs environment discovery, including reading the machine GUID, computer name, and supported languages.

At first glance, the HTTP panel is noisy: Microsoft update, telemetry, DigiCert OCSP, and login.live.com requests dominate the visible traffic. Those are largely whitelisted background communications. The malware-specific evidence comes from three aligned places: the MalConf panel, the DNS/Threats views, and the Connections panel, which shows PID 7660 connecting to donzola.duckdns.org at 192.169.69.26:2000 with malicious reputation.

Your task: reconstruct the archive-based execution chain, identify the fake installer payload, extract the real infrastructure, document what the malware actually did, and avoid making claims that the sample does not support.

💡 Reading this task as an analyst

Archive delivery → WinRAR is not just background noise here. It is the first important process because it shows how the executable entered the user context.

Process identity → The executable claims to be Maxthon Installer, but its random filename and execution context contradict that identity. This is weak masquerading rather than stealthy injection.

Network interpretation → The visible HTTP requests are mostly legitimate operating-system noise. But unlike the older draft of this workshop, the current task also shows actual malicious connection evidence in the Connections and DNS views. Use that.

STEP 5 — SEPARATE NOISE FROM REAL C2 EVIDENCE
What students should look for before checking the answer
  • Start with the HTTP Requests tab and identify entries marked whitelisted.
  • Then pivot to Connections, DNS Requests, Threats, and MalConf.
  • Check whether the malware PID itself owns a connection, not just system processes like svchost.exe.
  • Look for overlap between the domain in MalConf, the domain in DNS, and the domain/IP in Connections.
  • Do not write the answer until you can explain why Microsoft and DigiCert traffic is noise and why the DuckDNS entry is different.

📋 WHAT DID THIS INVESTIGATION DEMONSTRATE?
1 — Not every AsyncRAT sample is an injection case
This task is a direct-execution case, not a hollowed-process case. Good analysis starts with what the evidence actually shows, not with what a family is capable of in general.
2 — Archive delivery matters
The path from encrypted ZIP → WinRAR → Desktop executable → manual launch is itself a meaningful execution story and should be documented clearly in the timeline.
3 — Most visible HTTP traffic here is still noise
Windows telemetry, Microsoft update, login.live.com, CRL, and OCSP traffic dominate the HTTP list. The analyst’s job is to filter that out without missing the separate malicious connection evidence.
4 — MalConf is a pivot, not the whole story
In the current task version, the real AsyncRAT infrastructure is not just recovered from configuration extraction. It is also corroborated by a malicious DNS record and a live connection from the payload process to donzola.duckdns.org:2000.
5 — Absence of evidence is still evidence
Compare the extracted config with the captured registry/file activity before deciding whether persistence is actually supported in this run. Here, it is not.
