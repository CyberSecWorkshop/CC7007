Incident Timeline Reconstruction

🧠 WHAT ARE WE ACTUALLY DOING? — READ FIRST

In Workshop 5 (Evil's Den) you investigated a script-based attack: a Python script encrypted a file, hid a key inside a JPEG using steganography, and left artefacts in memory because Notepad windows remained open. The investigation was linear — find the files, reverse the crypto, extract the hidden data.

This workshop is different. Amadey is a live trojan stealer — malware that executes, establishes real network communications, plants persistence mechanisms, and harvests credentials, all while disguising itself as a legitimate Windows process. Your investigation must do more than find what happened. You must establish when each action occurred, in what order, using which technique, and map every step to the MITRE ATT&CK framework — because that is what a professional incident timeline report looks like.

What new skills does this add?

Volatility 3 syntax
This workshop uses Vol3, not Vol2. The command structure, plugin names, and profile handling are different. A direct comparison is provided in the next section.
Process masquerading
windows.pstree reveals a process named lssass.exe — one letter away from the legitimate Windows process lsass.exe. Spotting typosquatted process names is a core analyst skill.
Network IOC extraction
windows.netscan captures TCP connections active at time of dump — including live C2 beaconing. You will extract the C2 IP and port directly from memory.
Attack timeline construction
You will compile each finding into a structured timeline table: timestamp (where recoverable), event, evidence source, MITRE ATT&CK tactic, and analyst confidence level.

📁 THE CASE — READ BEFORE ANYTHING ELSE
// Case Reference: AMADEY-MEM-06 · Evidence type: Windows Memory Dump · Profile: Windows 7 x64

After-hours on a Tuesday, your organisation's Endpoint Detection and Response (EDR) system fires an alert against a Windows 7 workstation used by an employee in the finance department. The alert flags suspicious process behaviour consistent with the Amadey Trojan Stealer — a well-documented malware strain that specialises in reconnaissance, credential harvesting, and establishing persistent remote access.

The on-call analyst pulled a live memory dump before the machine was isolated. You have been handed the .vmem artifact and asked to produce a full incident timeline: what the malware did, in what order, and how it intended to survive a reboot. Legal have been notified — your timeline may be used in disciplinary proceedings.

The Amadey Trojan Stealer is known to: masquerade as a legitimate Windows process to avoid detection, establish encrypted C2 communications, plant persistence via the Windows Run registry key and the Scheduled Tasks folder, and harvest credentials from browser profiles and credential stores. Your task is to find the evidence of each of these behaviours in the memory dump and build a defensible chronological timeline.

💡 Reading the scenario as an analyst

Process masquerading → Look for processes with names one character different from legitimate Windows processes. lsass.exe vs lssass.exe is the classic Amadey typosquat. The process tree will reveal it.

C2 communications → windows.netscan captures TCP/UDP state at time of dump. An established outbound connection from a suspicious process to an unusual external IP is your C2 indicator.

Persistence → Two known Amadey persistence vectors: a value in the Windows Run registry key, and a copy of the executable planted in the Scheduled Tasks folder. Both are findable via memory.

STEP 1 — PROFILE THE DUMP

You already ran windows.info during setup. Use this section to record the key values and understand what they mean for the investigation.

🕐
The capture timestamp is your timeline anchor
Every relative timing inference starts here

The memory dump was captured at a specific moment. That timestamp — visible in windows.info output — is the latest possible time for every artefact you find in the dump. Any process, connection, or file handle you discover was active at or before that moment.

For absolute timing of earlier events (process creation times, file write times), you will use metadata extracted from specific artefacts — process creation timestamps from the EPROCESS kernel structure, connection establishment times from TCP objects. Not all of these will be available. Where they are not, you express timing relatively: "after initial execution, before capture".

This is a key concept at Level 7: a professional timeline distinguishes between what is known with certainty (direct timestamp evidence) and what is inferred (ordering based on logical dependencies). Your timeline table in Step 7 will include a confidence column for exactly this reason.

Pattern — every Vol3 command for this dump

STEP 2 — MAP THE PROCESS TREE
What we are trying to find out
  • Get a full picture of running processes and their parent-child relationships at time of capture
  • Identify any process with a name suspiciously similar to a legitimate Windows system process
  • Note which parent spawned the suspicious process — this is the initial access vector or the infection chain entry point
  • Note the PID of the malicious process — you will use it to filter output in every subsequent step
🌲
Why windows.pstree reveals what windows.pslist hides
Parent-child relationships are the forensic context

pslist gives you a flat list of all running processes. It tells you that lssass.exe exists. pstree shows parent-child relationships — revealing that lssass.exe has a parent PID (2524) that is no longer in the process list, meaning the dropper already self-terminated. The child rundll32.exe under it confirms a DLL payload is being loaded.

Legitimate lsass.exe (the Windows Local Security Authority Subsystem Service) is always a child of wininit.exe, which is itself a child of smss.exe. Seeing a process named lssass.exe (extra 's') with a missing or wrong parent is a definitive process masquerading indicator. The parent-child relationship is the evidence that confirms it — not just the name.

Run this
Full process tree with parent-child relationships

vol.py -f ~/Desktop/Start\ here/Artifacts/Windows\ 7\ x64-Snapshot4.vmem windows.pstree | tee ~/Desktop/amadey_output/pstree.txt

The tee command writes the output to a file and prints it to the terminal at the same time. You will reference this saved file rather than re-running the slow plugin multiple times. What to look for
  • lssass.exe (double 's') — PID 2748 — this is the malicious process. Record this PID now, you will use it to filter output in every subsequent step.
  • Parent PID 2524 is not visible in the tree — the parent process had already exited before the dump was captured. This is a deliberate defensive technique: the dropper launches the malware then self-terminates to reduce its footprint. The malware was still launched by a user-initiated process.
  • Legitimate lsass.exe: PID 508, child of wininit.exe (PID 400) — correct ancestry confirmed. This is what a real system security process looks like in the tree.
  • rundll32.exe (PID 3064) as a child of lssass.exe — rundll32.exe is a legitimate Windows utility for executing DLL files. Its presence as a child of the malicious process means Amadey is using it to load a downloaded DLL payload. Record this PID too.
  • CreateTime gap: 21:33:04 → 21:33:56 — lssass.exe launched, then 52 seconds later spawned rundll32.exe. This is the delay between initial execution and payload loading.

Malicious process: lssass.exe (PID 2748) — double 's', typosquat of legitimate lsass.exe
Parent PID 2524: not visible in tree — dropper self-terminated before capture
Child process: rundll32.exe (PID 3064) — used to execute downloaded DLL payload
Legitimate lsass.exe: PID 508, child of wininit.exe (PID 400) ✓
Malicious lssass.exe: PID 2748, parent exited ✗ — process masquerading confirmed
MITRE ATT&CK: T1036.005 — Masquerading: Match Legitimate Name or Location. The attacker named the malware one character away from lsass.exe — a critical Windows security process — to evade casual inspection. The missing parent (PID 2524 exited) is itself a defensive technique: the dropper self-terminates after launching the payload to leave fewer traces. The child rundll32.exe confirms a second-stage DLL is being loaded. Record PID 2748 before moving to Step 3.
STEP 3 — READ THE COMMAND LINES
What we are trying to find out
  • Where on disk was the malware executed from? The executable path is in the process arguments
  • Amadey typically stages itself in the user's AppData\Local\Temp folder — we want to confirm this
  • Were any arguments passed at execution? Arguments can reveal how the malware was invoked — by another process, a scheduled task, or directly by the user

OUTPUT
PID    Process         Args
...
2852   lssass.exe

What to look for
  • AppData\Local\Temp as the execution path — Amadey stages itself here because it is a user-writable directory that does not require elevation. Many endpoint security tools do not block execution from Temp.
  • The subdirectory inside Temp often has a random-looking name (hash or UUID) — this is the dropper creating an isolated staging folder to avoid name collisions with other temp files
  • No arguments beyond the path — Amadey typically runs with no command-line arguments. If you see arguments, record them — they may indicate a specific campaign configuration or a second-stage instruction
  • Record the full path — you will use it in Step 5 to find the file handle in memory
// Analogy — why Temp is a preferred staging location
Legitimate software routinely drops files in the Temp folder during installation. Security tools that block executable launches from Temp create too many false positives for everyday software. Attackers exploit this tolerance window. A mature security posture monitors which executables launch from Temp and flags those not associated with a known installer process — which is exactly what the EDR did to trigger this investigation.
STEP 4 — CAPTURE NETWORK STATE
What we are trying to find out
  • Whether the malicious process had any active or recently-established TCP connections at time of capture
  • The remote IP address and port — your C2 server indicator of compromise (IOC)
  • The connection state — ESTABLISHED means live C2 at time of capture; CLOSE_WAIT or TIME_WAIT means it had recently communicated
🌐
What windows.netscan actually captures
TCP objects from the kernel's network pool

Windows maintains kernel objects for each TCP connection — _TCP_ENDPOINT structures in the network pool. These contain the source address, destination address, ports, protocol, state, and the PID of the owning process. windows.netscan scans the kernel pool for these objects and presents them in a readable table.

Critically: netscan finds connections even if the process has since tried to hide them by closing the socket at the application layer, because the kernel pool object may not be immediately freed. It also finds connections from recently-terminated processes if the kernel object has not yet been reclaimed — this is the same pool persistence mechanism you saw with file handles in Workshop 5.

For the analyst: any ESTABLISHED connection from a process in the Temp folder to an external IP on an unusual port is a C2 indicator. Any connection from a process with a masqueraded name is a confirmed IOC.

What to look for
  • ESTABLISHED connection on port 80 from lssass.exe — C2 over HTTP (port 80) is a common Amadey technique. Using port 80 blends into normal web traffic, making it harder to block at the firewall without disrupting legitimate browsing.
  • The foreign IP address — record this. It is the C2 server IOC. You can submit it to VirusTotal or abuse.ch for threat intelligence enrichment outside this workshop.
  • State: ESTABLISHED — the malware was actively communicating at the moment the dump was taken. This is the strongest possible evidence of live C2.
  • Also check for any UDP connections — some Amadey variants use DNS over UDP for C2 channel establishment before switching to HTTP.

Source: lssass.exe (PID from Step 2) → Remote IP on port 80
State: ESTABLISHED — active communication at time of dump
Protocol: TCPv4 over HTTP (port 80) — blends with legitimate web traffic

Using HTTP on port 80 for C2 is deliberate — it traverses most firewalls without triggering alerts because port 80 is expected on corporate networks. The combination of a masqueraded process name (Finding 1) and C2 over a permitted port (Finding 2) is a classic Amadey dual-evasion pattern. The memory dump caught it because the kernel TCP object was live at time of capture.
STEP 5 — LOCATE MALWARE FILES IN MEMORY
What we are trying to find out
  • Where on the filesystem did Amadey plant its files? We already know the initial staging path from Step 3 — now we look for additional copies it may have dropped
  • Amadey is known to copy itself into C:\Windows\System32\Tasks — a location associated with scheduled tasks that gives the appearance of a legitimate Windows component
  • File handles in memory may reveal files that were opened by the malware but have since been deleted from disk — the same pool persistence mechanism from Workshop 5

STEP 6 — READ THE PERSISTENCE REGISTRY KEYS
What we are trying to find out
  • Whether Amadey added an entry to the Windows Run registry key — the most common Windows persistence mechanism
  • The exact value name and data (the command it will execute on reboot)
  • Which user account's Run key was modified — this tells us the privilege level the malware achieved
🗝
The Windows Run key — persistence 101
Every value here executes automatically on user login

The Windows registry Run key (HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run) instructs Windows to execute the named commands whenever the current user logs in. This is legitimate — many Windows applications use it. It is also the most common malware persistence mechanism precisely because it is so ordinary.

When Amadey adds a Run key entry pointing to C:\Windows\System32\Tasks\lssass.exe, it ensures the malware restarts after every reboot — without needing a service, driver, or any elevated permissions. The key can be set with standard user rights.

Volatility 3's windows.registry.printkey reads registry hive data directly from memory, without needing to mount the registry from disk. The in-memory registry reflects the state at time of capture — including any modifications the malware made that have not yet been flushed to disk.

Run this
Read the Run registry key for the current user
HKCU Run key — current user (HKCU maps to the logged-in user's hive)
VOL3
vol.py -f ~/Desktop/Start\ here/Artifacts/Windows\ 7\ x64-Snapshot4.vmem windows.registry.printkey --key "SOFTWARE\Microsoft\Windows\CurrentVersion\Run"
💡 Also check the system-wide Run key (HKLM)

The above command checks the user-level Run key. If Amadey gained elevated privileges, it may have written to HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run instead — this persists for all users on the machine. Run the same command with the HKLM path to check both.

Representative output — malicious Run key entry
OUTPUT

What to look for
  • An entry named "lssass" pointing to Tasks\lssass.exe — this is the persistence mechanism. On next login, Windows will execute this file automatically, re-establishing the C2 connection and the masqueraded process.
  • The Tasks folder path as the execution target — this connects Finding 3 back to Step 5. The file you found in Tasks is not just present — it is wired into the Run key to guarantee execution on reboot.
  • Compare the malicious entry to the legitimate ones (like OneDriveSetup) — legitimate Run key entries point to standard Windows directories, not Tasks. The Tasks folder as an execution path is unusual and should be flagged regardless of the filename.
⚑ Finding 3 — Two Persistence Mechanisms Confirmed
Persistence 1 — Scheduled Task Location:
File: C:\Windows\System32\Tasks\lssass.exe (found via windows.filescan)

Persistence 2 — Registry Run Key:
Key: HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run
Value name: lssass
Value data: C:\Windows\System32\Tasks\lssass.exe
Evidence: windows.registry.printkey — in-memory registry hive
MITRE ATT&CK: T1547.001 — Boot or Logon Autostart Execution: Registry Run Keys / Startup Folder. The attacker used the Run key to ensure the malware restarts on every login, pointing at the copy hidden in the Tasks folder. T1053.005 — Scheduled Task/Job: Scheduled Task is the secondary classification — placing an executable in the Tasks folder exploits the implicit trust Windows grants to that directory. The dual-persistence approach means removing only the Run key would leave the binary in place, and removing only the binary would leave the Run key pointing to a missing file — creating a forensic footprint that would still alert a defender doing registry analysis.
STEP 7 — BUILD THE ATTACK TIMELINE
What we are building
  • A structured, chronological table of every confirmed event from the investigation
  • Each row: timestamp (or relative ordering if absolute timing is unavailable), event description, evidence source, MITRE ATT&CK tactic + technique, and confidence level
  • This is the deliverable — the document that goes to IR team lead, legal, and management
  • Incomplete evidence should be flagged as Medium or Low confidence — not omitted. Gaps are as significant as findings.
📋
What makes an incident timeline defensible?
The standard your Level 7 timeline must meet

A timeline used in a disciplinary proceeding or legal case must survive challenge. The opposing party will ask: how do you know this happened before that? and what is the source of that timestamp? Every time-ordered claim needs an evidentiary basis.

Where kernel timestamps are available (process creation time from the EPROCESS structure, file modification time from the MFT), use them and cite the source. Where they are not, express ordering logically: C2 communication requires process execution, which requires initial infection — so the ordering is: infection → execution → C2, even if only the C2 timestamp is available from netscan.

The confidence column communicates epistemic honesty. High confidence means a direct timestamp from a forensic artefact. Medium means a logical inference with strong support. Low means circumstantially supported but not directly evidenced. Never assign High confidence to an inference.

// Why the timeline matters beyond the technical findings
A memory dump on its own is a forensic artefact with no inherent narrative. The timeline is the analyst's translation of raw evidence into a story that a decision-maker can act on. The IR team lead needs to know what to eradicate and in what order — the timeline tells them. Legal needs to know when the malware was active relative to data access events — the timeline tells them. Management needs to know how long the attacker had access — the timeline tells them. Raw plugin output does not.
📋 WHAT DID THIS INVESTIGATION DEMONSTRATE?
1 — Process trees reveal what flat lists conceal
windows.pslist would show lssass.exe. windows.pstree reveals that lssass.exe is a child of explorer.exe, not wininit.exe — which is the single piece of evidence that confirms process masquerading. The parent-child relationship is often more diagnostic than the process name itself. An analyst who only runs pslist misses the most important context.
2 — Live memory catches what disk forensics misses
The ESTABLISHED C2 connection to the remote IP existed only in memory — it was active at time of capture and would not appear in any disk artefact. No log file on the machine would have recorded this in real time. The kernel TCP object in the network pool was the only evidence of live C2. Disk forensics conducted after network isolation would have found no connection evidence at all.
3 — Dual persistence means dual eradication requirements
Amadey plants two persistence mechanisms intentionally. Remove the Run key and the binary survives in Tasks, ready to be re-executed. Remove the Tasks binary and the Run key points to a missing file, creating a forensic trace that alerts the defender — but the malware can redrop itself on next C2 connection. Complete remediation requires identifying and removing both before the machine reconnects to the network. The timeline made this clear.
4 — Always use the full windows. plugin namespace
Vol3 ships with plugins for Windows, Linux, and Mac. Typing just pstree is ambiguous — Vol3 will error with "plugin matches multiple plugins". The fix is always the full namespace: windows.pstree, windows.netscan, windows.filescan. No --profile flag is ever needed — Vol3 auto-detects the OS from the dump's kernel structures, which is the key improvement over Vol2.
5 — A timeline with honest confidence levels is more valuable than a complete-looking one
The credential harvesting row was marked Low-Medium confidence because it came from threat intelligence, not this dump's evidence. That distinction matters. Presenting inferred events as confirmed facts in a legal or disciplinary context can invalidate an entire investigation. The confidence column is not a weakness in the timeline — it is a demonstration of analytical rigour. Reviewers at Level 7 and above will specifically evaluate whether you distinguish evidence from inference.
