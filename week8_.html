PART 2 — PROCESS TREE

⏱ ~25 min · Process Tree panel — left side of the any.run interface

The process tree is the most forensically informative panel in any sandbox report. It shows every process that ran, in parent-child order, with colour-coding for injection and suspicious activity. For AgentTesla, the tree typically contains three or four nodes: the initial dropper, a copy of itself in AppData, a legitimate host process into which it injects, and occasionally a child spawned for specific tasks.

🌳
Why the process tree is the backbone of the investigation
Everything else — network, files, registry — traces back to a process

Every action a piece of malware takes is performed by a specific process. Network connections come from a process. Files are written by a process. Registry keys are created by a process. The process tree tells you which process did what — and crucially, which process should not exist at all. A legitimate Windows binary that appears in the tree as a child of a newly-dropped executable is immediately suspicious, regardless of what its name is. That pattern — legitimate process, illegitimate parent — is the core indicator of process hollowing and process injection.

In any.run, injected processes are shown with a syringe icon (💉). Processes flagged as malicious have a red background. Processes spawned from unusual paths (AppData, Temp, ProgramData) have warning indicators. Start from the top of the tree and work downward — the story is always told from parent to child.

AgentTesla typically runs three or four hops deep, not two. A real sample might go: explorer.exe → wscript.exe (the initial script) → powershell.exe (launched with bypass flags) → aspnet_compiler.exe (the injected host). Each hop adds a layer of indirection. Understanding which hop introduced the malicious behaviour is the analytical task — the injection always happens at or near the end of the chain.

Task 2.1 — Read the Process Tree Top-Down

🖥 any.run Report
Process Tree panel — left side of the sandbox view

The process tree is visible on the left side of the any.run report by default. Each node shows the executable name, PID, and parent PID. Coloured indicators show status. Click any node to expand its details in the right panel — command line arguments, file path, timestamps, and any detected behaviours attributed to that process.

Real AgentTesla execution chain — your process names and PIDs will differ
PROCESS TREE
explorer.exe  PID 1528  (user shell — user double-clicked the file)
└── wscript.exe  PID 1068  ← initial JS script  MALICIOUS
    │  CMD: "C:\Windows\System32\WScript.exe" invoice.txt.js
    │  Note: file extension is .js disguised as .txt — Windows hid the real extension
    │
    ├── powershell.exe  PID 4304  ← launched by wscript  MALICIOUS
    │   CMD: -ExecutionPolicy Bypass -NoProfile -WindowStyle Hidden -File "C:\Temp\ps_[random].ps1"
    │   └── aspnet_compiler.exe 💉  PID 8252  ← injected host  INJECTED / AGENTTESLA
    │       (all credential theft, SMTP exfiltration, and browser access runs here)
    │
    └── taskkill.exe  PID 7780  ← anti-forensic cleanup
        CMD: /f /im wscript.exe   ← malware killing its own launcher after injection
What to look for
  • The parent of wscript.exe — what launched the script? If it is explorer.exe, the user double-clicked it. If it is winword.exe or excel.exe, a macro launched it. The parent reveals the delivery mechanism and maps to your first timeline event.
  • The file extension trick — a file named invoice.txt.js displays as invoice.txt on a Windows machine with "Hide extensions for known file types" enabled (the default). This is a social engineering technique. Note it in your Finding 1 as the delivery mechanism detail — T1036.007 Masquerading: Double File Extension.
  • The PowerShell flags — -ExecutionPolicy Bypass -NoProfile -WindowStyle Hidden are three separate defence evasion choices: bypassing execution policy, skipping profile scripts that might alert, and hiding the window from the user. Each one is a detectable IOC at the command-line logging level.
  • The injected target process — common targets are aspnet_compiler.exe, RegSvcs.exe, AppLaunch.exe, or vbc.exe. All are legitimate signed .NET binaries. Record the exact path and PID — you need the PID in Part 3 to attribute the SMTP connection to the right process.
  • taskkill.exe killing wscript.exe — the malware cleans up its own launcher after injection succeeds. This is anti-forensic behaviour: if an analyst only checks running processes after the infection, wscript.exe is already gone. It tells you the initial script execution has fully completed by the time taskkill fires — injection was successful.

PART 3 — NETWORK ACTIVITY

⏱ ~25 min · Network tab in any.run — DNS, connections, HTTP/SMTP

AgentTesla's exfiltration channel is the most operationally significant finding in the report. Different campaigns use different channels: SMTP on port 587 (most common), HTTP POST to a web panel, FTP, or even Telegram bot API. The network panel in any.run records every connection the sandbox observed, attributed to the process that made it.

📡
Exfiltration channel determines containment priority
The response action depends on what protocol the stolen data left on

If AgentTesla uses SMTP, the stolen credentials were sent as an email to an attacker-controlled mailbox. Containment means blocking the SMTP server's IP at the perimeter and resetting all passwords before they can be used. The email address in the SMTP headers is itself an IOC — it may be a compromised legitimate account used as a drop box.

If it uses HTTP, there is a web panel — a PHP script running on a compromised or attacker-owned server. The POST URL, the server IP, and any cookies or headers are all IOCs. If it uses Telegram, the bot token and chat ID are extractable from the malware's configuration and constitute persistent IOCs since Telegram bots are not trivially blocked at the network level.

Whatever channel your sample uses, the network panel gives you the destination IP or domain, the port, and often the transmitted content — enough to identify the attacker's infrastructure and notify relevant abuse contacts.

  • checkip.dyndns.org or api.ipify.org — almost every AgentTesla sample queries a public IP-lookup service before exfiltrating. This confirms the infection is active and the malware is preparing to include the victim's external IP in its exfiltration payload.   • Record every domain that is not a recognisable legitimate service — all of them are IOCs for your Part 5 export.

Task 3.2 — TCP Connections Panel and MalConf: Where SMTP Actually Lives

⚠️ Critical: SMTP does not appear in the HTTP requests panel

This is the most common mistake in sandbox network analysis. The HTTP requests panel in any.run only shows HTTP and HTTPS traffic. SMTP is a completely separate protocol — it never appears there. If you open the HTTP panel and see only whitelisted Microsoft background requests (Windows Update, CRL checks, login.live.com), that does not mean the malware made no network connections. It means the malicious connection used a different protocol. Always check the TCP Connections panel separately.

📭
Two separate evidence sources for the exfiltration channel
Observed traffic vs extracted configuration — different confidence levels

TCP Connections panel (Network tab → Connections): Shows every raw TCP/UDP session the sandbox observed, including SMTP on port 587. Each entry shows the source process PID, destination IP, destination port, and byte counts. This is observed behaviour — High confidence evidence. If the SMTP session appears here attributed to the injected process PID from Part 2, the exfiltration happened during the sandbox run.

MalConf panel: any.run decompiles the .NET assembly and extracts the hardcoded C2 configuration directly from the binary — the SMTP server hostname, port, username, and password the malware was programmed with. This is extracted configuration — it proves the malware would have exfiltrated to that server even if the sandbox run ended before the connection fired. It is Medium confidence: you know the intended destination but cannot prove data left the network in this specific run.

Both are IOCs. The distinction matters for your timeline confidence labels and for how you brief the IR team — a High confidence observed SMTP connection means credentials definitely left the network. A Medium confidence MalConf extraction means you need to treat it as if they did and act accordingly, but you cannot prove it yet.

⚠️ Do not reproduce SMTP credentials in your WebLearn submission

The MalConf panel may expose the attacker's SMTP password in plaintext. Record the structural IOCs — the hostname, port, and sender address — and write "credentials present — not reproduced" in your Finding 2. Do not paste the password into a discussion board post. The hostname and IP are your actionable IOCs; the password is only useful if you are reporting the account to the mail provider's abuse team, which is outside the scope of this workshop.

What to record from Connections and MalConf
  • From TCP Connections: destination IP and port 587 attributed to the injected process PID — this is High confidence direct evidence of an attempted or completed SMTP exfiltration. The IP is your primary firewall block IOC.
  • From MalConf — the hostname — resolve it with a DNS lookup to confirm it matches the IP in Connections. If they match, two independent evidence sources confirm the same C2 server. If they differ, the malware may have multiple C2 servers configured.
  • From MalConf — the sender address domain — often a compromised legitimate business mail server rather than an attacker-registered domain. Check the registrar and hosting country. This tells you whether to report to a hosting provider (attacker infrastructure) or to a business whose mail server was compromised.
  • Whether the connection appeared in Connections or only in MalConf — this determines whether the confidence level in your timeline is High (observed) or Medium (configured but not confirmed as executed in this run).

The key distinction for your timeline: if the SMTP connection appeared in the TCP Connections panel attributed to the injected PID, confidence is High — credentials were exfiltrated. If only the MalConf extraction is present, confidence is Medium — the malware was configured to exfiltrate but the connection was not observed in this run window. Both warrant the same immediate containment action (block the destination IP), but the confidence label is different and matters for how the finding is communicated.
PART 4 — FILE AND REGISTRY ACTIVITY

⏱ ~20 min · File Activity and Registry tabs in any.run

Persistence is what separates a single infection from a sustained compromise. If AgentTesla writes a registry Run key, it survives every reboot until that key is removed. If it creates a scheduled task, it survives even if the Run key is cleaned. Understanding exactly what was written — and where — defines the remediation checklist that the IR team uses to clean the affected host.

Task 4.1 — Dropped Files

🖥 any.run Report
Files tab — every file created or modified during the sandbox run

Click the Files tab. The panel lists every file the malware created, modified, or deleted. Each entry shows the full path, the process that created it, and the file hash. Focus on files created in user-writable locations — system directories are usually reads, not writes.

Typical AgentTesla file drops — your paths will differ
FILES TAB
Created by Invoice_INV-2024-08841.exe  PID 3044:
  C:\Users\admin\AppData\Roaming\SubFolderX\malware_copy.exe  ← persistence copy
  C:\Users\admin\AppData\Local\Temp\tmp4F2A.tmp             ← temp working file

Created by RegSvcs.exe  PID 4156:
  C:\Users\admin\AppData\Roaming\SubFolderX\log.tmp         ← keylog buffer
What to look for
  • The self-copy in AppData\Roaming — record the full path exactly, including the subdirectory name which is often randomised per-infection. This path is the primary artefact for host-based detection and remediation.
  • A .tmp or .log file in AppData — AgentTesla maintains a local buffer of keylog data before transmitting it. This file may contain captured keystrokes from the sandbox VM's test input. Record its path for the remediation checklist.
  • The hash of the dropped copy — click the file entry to see its SHA-256. It may differ from the original sample hash if the malware modified itself during the copy. Both hashes are IOCs.

Task 4.2 — Registry Persistence

🖥 any.run Report
Registry tab — filter for WRITE operations in Run keys

Click the Registry tab. The panel lists every registry operation observed during the run: reads, writes, and deletes. Filter for Write operations and look for entries under the well-known persistence paths below.

Registry write — persistence via Run key
REGISTRY TAB

PID:   3044  (Invoice_INV-2024-08841.exe — the dropper writes its own persistence)
💡 HKCU vs HKLM — the significance of the hive

HKCU (Current User) persistence requires no administrator privileges — any standard user account can write it. This means AgentTesla establishes persistence without triggering a UAC prompt, making the infection fully silent from the user's perspective. HKLM (Local Machine) persistence would require admin rights and is less common in AgentTesla campaigns. Note which hive your sample uses — it affects the remediation approach.

Also check for scheduled tasks
  • Some AgentTesla samples create a scheduled task as a secondary persistence mechanism alongside the Run key. Look for registry writes under HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache or file writes to C:\Windows\System32\Tasks\.
  • If both a Run key and a scheduled task are present, document both — remediation must address both or the malware will recover after the Run key is deleted.
⚑ Finding 3 — Persistence Mechanism Confirmed from Registry and File Activity
Persistence type: Registry Run Key [+ Scheduled Task if present] Registry key: [full key path — HKCU or HKLM] Value name: [registry value name] Value data: [full path to self-copy in AppData] File artefact: [full path and SHA-256 of the dropped copy] Writing process: [dropper filename] PID [number] Keylog buffer: [path to .tmp or .log file if present]
MITRE ATT&CK: T1547.001 — Boot or Logon Autostart Execution: Registry Run Keys. The HKCU Run key written by the dropper ensures AgentTesla reloads after every user login without requiring administrator rights. Remediation requires deleting the registry value, removing the self-copy from AppData, and — if a scheduled task was also created — deleting that task. If only the registry key is removed, a scheduled task variant will reinstall it at the next login. Record the full registry path and file path so the IR team can verify removal on the host.

PART 6 — IR EVIDENCE PACK

⏱ ~35 min · Four deliverables · Submit as a single document on WebLearn

You have now completed five parts of evidence collection. Part 6 asks you to produce four specific deliverables from what you found — the same four things a real analyst hands off at the end of a sandbox investigation. Together they form your IR Evidence Pack: the document that travels from the analyst to the IR team, the CISO, and the IT remediation team.

📦
Why four deliverables instead of one timeline
Different audiences need different views of the same evidence

A timeline answers "what happened and when?" — useful for the IR analyst and the legal team. But the person who configures the firewall needs a prioritised IOC list, not a narrative. The IT engineer cleaning the infected host needs a remediation checklist with specific registry paths and file locations. The CISO briefing the board needs two sentences that explain the business risk without technical jargon. The same investigation produces all four — and an analyst who can only produce the timeline is doing a fraction of the job.

This is also the task that most clearly differentiates depth of analysis. A surface-level investigation produces a thin timeline with three rows and vague IOCs. A thorough investigation produces a timeline with eight rows, a prioritised IOC table with confidence levels and rationale, a complete remediation checklist, and a well-written executive summary. The evidence does not change — the analytical quality does.

Deliverable 1 — MITRE ATT&CK Timeline

Build a table that orders every observable event from the infection chronologically, maps each to a MITRE ATT&CK technique, and assigns a confidence level. Every row must be sourced to a specific any.run panel — not to the report in general.

📐 Required columns

1. Timestamp — relative time from sandbox start (T+0s, T+4s, T+62s etc.) Use "Pre-capture" for events before the sandbox run.

2. Event — one specific sentence. Name the file, the PID, the IP address, the registry key. No vague descriptions like "malware executed."

3. Evidence Source — the exact panel. "Process Tree → wscript.exe node, CMD field" or "TCP Connections panel, aspnet_compiler.exe PID 8252 → port 587." Never just "any.run report."

4. MITRE ATT&CK — sub-technique ID and name. T1059.007 not T1059. Use IDs from the ATT&CK tab, not from memory.

5. Confidence — High (directly observed), Medium (inferred from observed indicators + known TTP), or Low (threat intelligence — not observed in this run).

Events your timeline must cover — at minimum
  • Phishing email delivery — pre-capture. Low confidence. Source: AgentTesla threat intelligence. Why include it? The remediation team needs to know to quarantine the email and check for other recipients in the mail server logs.
  • User opened the .js file — inferred from explorer.exe as parent of wscript.exe. Medium confidence. The parent process confirms it was a user desktop action, not a scheduled task or a macro.
  • wscript.exe executed the JavaScript — T+0. Process Tree. High confidence. Note the file extension trick if present.
  • PowerShell launched with bypass and hidden flags — T+[n]s. Process Tree, powershell.exe CMD field. High confidence. Three separate evasion techniques in one command line.
  • Payload dropped to C:\Temp — T+[n]s. Files tab, wscript.exe drop. High confidence. Full path and hash.
  • aspnet_compiler.exe injected — T+[n]s. Process Tree, injection icon. High confidence. This is the pivot point — everything malicious after this row comes from the injected process.
  • taskkill.exe killed wscript.exe — T+[n]s. Process Tree. High confidence. Anti-forensic indicator removal — T1070.004.
  • Browser credential stores accessed — Behaviour tab, aspnet_compiler.exe. High or Medium depending on what your panel shows directly.
  • SMTP exfiltration to C2 server — TCP Connections or MalConf. High if observed, Medium if MalConf only. Full IP and port.
  • Persistence written — Registry tab or not observed. If not observed, Low confidence row sourced to known AgentTesla behaviour. Still include it — the remediation team checks for it regardless.

Deliverable 2 — Prioritised IOC Table

The IOC table is what you hand to the firewall engineer and the threat intelligence platform team. It is not a dump of everything any.run found — it is a prioritised, annotated list that tells each recipient which IOC to act on first and why.

💡 Prioritisation is the analytical work — not the list itself

any.run's automated IOC export gives you the list. The table you build adds the prioritisation, the rationale, and the recommended action for each indicator. That is what makes it useful to the person receiving it. A list of 15 hashes with no context helps nobody. A table of 8 prioritised IOCs with "block immediately," "monitor," and "report to provider" annotations drives action.

Required columns for your IOC table
TABLE STRUCTURE

IP address    [C2 SMTP server IP]   TCP Connections   High        IMMEDIATE   Block outbound port 587 to this IP
Domain        [mail.domain.com]     DNS + MalConf     High        IMMEDIATE   Block DNS resolution + report to registrar
SHA-256       [injected PE hash]    Process Tree      High        HIGH        Add to AV exclusion / EDR detection rule
File path     [C:\Temp\ps_*.ps1]    Files tab         High        HIGH        Hunt for this path pattern across all hosts
Registry key  [HKCU\...\Run\*]      Registry tab      Med/High    HIGH        Check and remove on affected host
SHA-256       [original sample]     Overview panel    High        HIGH        Add to email gateway block list
SMTP sender   [address@domain]      MalConf           Medium      MEDIUM      Report to mail provider abuse team
SMTP passwd   credentials present   MalConf           —           —           Do not reproduce — report to provider only
What makes a good IOC table
  • Immediate vs High vs Medium priority — the SMTP server IP gets Immediate because blocking it stops live exfiltration. The file path gets High because hunting for it across the fleet identifies other infected machines. The SMTP sender address gets Medium because reporting it depends on a third party responding.
  • Every IOC sourced to a specific panel — "MalConf tab" and "TCP Connections, port 587" are specific. "Network activity" is not. If you cannot name the panel, you cannot be sure the IOC is real.
  • Confidence reflects observed vs configured — an IP from the TCP Connections panel (observed behaviour) is High. The same IP from MalConf only (extracted configuration) is Medium. This distinction tells the firewall engineer whether the block is containment or precautionary.
  • Do not include whitelisted Microsoft IPs — the automated export may include Windows Update and CRL check IPs. These are not malicious. Filtering them out is part of the analytical work.

⚠️ Persistence not observed ≠ persistence not present

If the registry tab in your sandbox report showed zero write events, that does not mean the malware has no persistence mechanism. The sandbox run may have ended before the persistence code executed — many AgentTesla samples write persistence only after the first successful exfiltration. Include the registry Run key check in your remediation checklist regardless, sourced to "known AgentTesla persistence behaviour — not directly observed in this run window." The engineer checks it anyway. If it is there, it gets removed. If it is not, nothing was lost by checking.

Deliverable 4 — Executive Summary

Two paragraphs. No technical jargon. Written for a non-technical manager or CISO who needs to understand what happened, what data is at risk, and what is being done about it — in under two minutes of reading.

📄
What makes an executive summary effective
The audience does not know what aspnet_compiler.exe is — and should not have to

Paragraph 1 — What happened: One or two sentences on the incident. No process names, no port numbers. Example: "A malicious file disguised as an invoice was opened on a finance workstation. It silently installed credential-stealing software that captured saved passwords from the browser and attempted to transmit them to an external server." That is the entire technical story, translated.

Paragraph 2 — What is at risk and what is being done: Be specific about the data category — "browser-stored passwords, potentially including email and financial accounts" — and state the containment and remediation actions in plain language: "The infected machine has been isolated. The destination server has been blocked at the network perimeter. Affected passwords are being reset." End with the confidence level: "Analysis of the malware's configuration confirms the intended destination — we are treating all passwords on this machine as compromised regardless of whether transmission was completed."

The hardest part of an executive summary is resisting the urge to include technical detail to demonstrate rigour. The detail belongs in the timeline and IOC table. The summary's job is to drive decisions, not to impress with knowledge.

📋 WHAT DID THIS INVESTIGATION DEMONSTRATE?
1 — A sandbox report is a complete behavioural record, not just a verdict
The threat score and family label at the top of any.run tells you what the malware is. The process tree, network panel, file activity, and registry tabs tell you what it did — and in enough detail to drive a remediation checklist, an IOC export, and an incident timeline. A sandbox is not a yes/no malware detector. It is a forensic environment.
2 — Process injection hides malicious network activity inside legitimate processes
Every network connection and credential access in this run came from a legitimate Windows binary (RegSvcs.exe, AppLaunch.exe). A network log showing connections from a signed Microsoft process looks benign — until you trace the process tree and see it was spawned by a newly-dropped executable from AppData. The parent-child relationship is what exposes the deception.
3 — The exfiltration channel determines the response action
SMTP exfiltration means credentials were emailed to an attacker inbox — block the SMTP server IP and reset all passwords. HTTP exfiltration means there is a web panel — block the panel IP and investigate what other victims may have uploaded to it. Telegram means a persistent bot endpoint that cannot easily be network-blocked. Identifying the channel is not just academic — it directly changes the actions the IR team takes in the first 30 minutes of response.
4 — Automated IOC extraction is not a substitute for manual analysis
any.run's automated IOC export is fast and comprehensive for technical indicators. But it does not make analytical judgements: it does not tell you which IOC is highest priority, why the HKCU Run key matters more than the Temp file, or what the SMTP recipient address tells you about the attacker's infrastructure. Manual analysis adds the context and prioritisation that turns a list of indicators into an actionable intelligence product.
5 — The IR Evidence Pack is four different views of the same evidence
The timeline answers "what happened and when." The IOC table answers "what do I block and in what order." The remediation checklist answers "what do I remove from the host." The executive summary answers "what does this mean for the business." One investigation — four audiences — four documents. The analytical skill is not finding the evidence, which the sandbox largely does for you. It is translating the evidence into the form that is useful to each recipient and making the prioritisation judgements that drive action.
