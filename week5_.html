Script Recovery & Steganography

🧠 WHAT ARE WE ACTUALLY DOING? — READ FIRST

Last workshop you analysed the MemLabs Lab 2 — Alissa Simpson image — a scenario focused on user activity reconstruction: finding a deleted file, recovering a password, and identifying what a suspect was doing at time of capture. That investigation was about user artefact recovery: process context, registry traces, and file recovery.

This workshop is different. The attacker here is not running persistent malware — they have executed a script that encrypted sensitive data and then cleared the visible traces. The encrypted file is still on the machine, but the key is hidden in steganography inside an image file. The only way to recover the information is to dig both artefacts out of memory and chain them together.

What new skills does this add?

File carving from memory
filescan + dumpfiles — locate and extract files that were open in memory, even if deleted from disk
Reading command history
cmdline reveals the exact arguments passed to every running process — including what files were open in Notepad
Reversing simple encryption
A Python XOR + Base64 script encrypted a secret. You will reverse it using CyberChef — no programming required
Steganography extraction
steghide extracts data hidden inside a JPEG image — requiring the first flag half as the passphrase. Evidence chains matter.

📁 THE CASE — READ BEFORE ANYTHING ELSE
// Case Reference: EVILD-MEM-03 · Evidence acquired: 2018-09-30 · Profile: Win7SP1x86

An employee at a small software firm is suspected of exfiltrating proprietary source code before resigning. The IT team observed suspicious Python activity on the workstation shortly before the user logged off. A memory dump was taken from the live machine before shutdown.

Initial triage of the hard drive found a file called vip.txt on the Desktop containing what appeared to be a base64-encoded string — but decoding it produced garbled output. A file called evilscript.py was also present.

The IT team could not read the script's logic without running it, and they do not want to execute untrusted code. There is also a JPEG image on the Desktop that has not been examined. Your task: extract both files from the memory dump, reverse the encryption on vip.txt, and determine whether the image contains hidden data.

💡 Reading the clues

Garbled base64 output → The data was XORed before being base64-encoded. Raw base64 decoding will not work — you need to reverse both operations in the correct order: decode base64 first, then XOR. The script in memory reveals the XOR key.

JPEG image on the Desktop → Images are a common steganography carrier. steghide can embed files inside JPEG images invisibly. The hidden content is password-protected with the first half of the flag.

Files were open at time of capture → Even if a user closes a file or tries to delete it, if any process had it open in the minutes before the dump, filescan will find its memory-backed handle and dumpfiles can extract it.

STEP 1 — PROFILE THE IMAGE

You already ran this during setup. This section explains what the profile means and why you should write it down verbatim.

🗺
Why Win7SP1x86_23418 and not just Win7?
Profiles are not interchangeable across service packs

Volatility profiles are precise maps of how a specific Windows version arranges data in kernel memory. Microsoft changed internal data structures between service packs and even between build numbers. A profile for Windows 7 SP1 build 23418 has different memory offsets than SP0 or a different build of SP1.

Using the wrong profile means every plugin reads data from the wrong memory location. You might get output — it will just be wrong. Always use the full suggested profile string as-is.

Compare this to the MemLabs 2 image (Workshop 4) which used Win7SP1x64 — the same OS but 64-bit. That dump's kernel structures are completely different. Profile is not just about the OS version — it is about the exact binary build.

Reference — profile to use in every remaining command

STEP 3 — READ THE COMMAND HISTORY
What we are trying to find out
  • Every process stores its launch command in memory — including the arguments that were passed to it
  • When Notepad opens a file, the filename becomes part of the command: NOTEPAD.EXE C:\Users\hello\Desktop\evilscript.py
  • This plugin will reveal exactly which files the two Notepad instances had open — without having to look at the hard drive at all
  • This is one of the most underrated Volatility plugins for insider threat investigations: it tells you what the user was reading and editing at the exact moment of capture
📋
What cmdline actually shows
Process arguments, not shell history

Unlike the Windows command prompt history (which you would get with the cmdscan or consoles plugin), cmdline reads the PEB (Process Environment Block) of each process — the kernel structure that stores how the process was invoked, including its full argument list.

This is separate from shell history. Even if the user used PowerShell to run something and then closed it, the running processes that are still alive will have their argument strings in their PEB. A Notepad window that is still open will always show what file it is editing — even if the user has tried to hide the file since.

STEP 4 — FIND FILES IN MEMORY
What we are trying to find out
  • We know the filenames. Now we need to find their physical addresses in memory — the offset values needed to extract them
  • filescan scans the Windows file object pool in memory and lists every file that had an open handle at time of capture
  • We want the offsets (hex addresses) for: evilscript.py, vip.txt, and — critically — any JPEG on the Desktop
🗂
Why filescan finds files even if they were "deleted"
File objects in the Windows kernel persist beyond deletion

When a Windows process opens a file, the kernel creates a File Object — a kernel-mode data structure that holds a reference to that file. This object persists in the kernel object pool as long as any process has the file open, even if the file has been deleted from the filesystem.

If the attacker deleted evilscript.py but forgot to close Notepad, the File Object for the script is still in memory. filescan scans the pool allocator for File Object signatures and lists them all. The offset it returns is the address of that File Object — which dumpfiles then uses to extract the file's actual data.

This technique can recover files that were deleted from disk hours before the dump — as long as something kept them open in memory.

STEP 6 — REVERSE THE ENCRYPTION
What we are trying to do
  • Read the Python script to understand what it did to the plaintext
  • Identify the XOR key used to encrypt the original string
  • Use CyberChef to reverse both operations (Base64 decode → XOR with key) and recover the plaintext
  • The recovered plaintext is the first half of the flag

The encryption script — reading evilscript.py

Contents of evilscript.py — extracted from memory
PYTHON
import sys
import string

def xor(s):
    a = ''.join(chr(ord(i) ^ 3) for i in s)   ← XOR key is 3
    return a

def encoder(x):
    return x.encode("base64")                   ← then base64-encode

if __name__ == "__main__":
    f = open("C:\\Users\\hello\\Desktop\\vip.txt", "w")
    arr = sys.argv[1]           ← takes the secret string as a command-line argument
    arr = encoder(xor(arr))     ← XOR first, THEN base64
    f.write(arr)
    f.close()
🔐
Understanding what the script did
And how to reverse it step by step

The script takes a secret string as a command-line argument, XORs every character with the integer 3, and then base64-encodes the result before writing it to vip.txt.

To reverse this, you do the operations in the opposite order: first base64-decode the content of vip.txt, then XOR every byte of the result with key 3 again. XOR is its own inverse — XORing twice with the same key returns the original value.

You do not need to write any code. CyberChef has a "From Base64" operation and an "XOR" operation. Chain them in reverse order and the plaintext appears.

// Analogy — XOR is reversible
XOR with a fixed key is like a lock where the key both locks and unlocks. If you press A XOR 3, you get B. If you then press B XOR 3, you get A back. This is why XOR is so common in simple encryption — and why it is trivially broken when the key is known or can be brute-forced.

🖼
What is steganography and why does it matter forensically?
Hiding data in plain sight — inside ordinary-looking files

Steganography is the practice of hiding a message inside another, innocent-looking file in a way that is not visible to casual inspection. The word comes from the Greek for "hidden writing." Unlike encryption (which scrambles data so it is unreadable), steganography hides the fact that a message exists at all.

A JPEG image has redundancy in its pixel data — the least-significant bits of pixel values can be modified without any perceptible change to the image. steghide exploits this by embedding a payload (any file) across those least-significant bits. The image looks completely normal when viewed in an image viewer.

In a forensic context: an investigator who only looked at the image visually would never suspect it contained the second half of an attacker's flag. Only memory forensics — finding the image in memory, extracting it, and running steghide — reveals the hidden content. The passphrase requirement adds a second layer: even if an analyst found the image, they would need the XOR-decrypted key to extract it.

// Analogy — steganography vs encryption
Encryption is a locked safe — everyone can see the safe exists, but they cannot open it. Steganography is a message written in invisible ink on a postcard — no one knows there is a message at all. The attacker here used both: encrypting the flag half in vip.txt (locked safe) and hiding the second half in the JPEG (invisible ink). Recovering it required finding the safe's contents first, then using that to read the invisible ink.

📋 WHAT DID THIS INVESTIGATION DEMONSTRATE?
1 — cmdline reveals what the user was doing at time of capture
Process arguments are stored in the PEB and persist in memory as long as the process is alive. Two Notepad windows with specific files open told us exactly what the attacker was reviewing. This would not appear in any log file or disk artefact — it is purely volatile intelligence.
2 — filescan recovers files that may have been deleted from disk
Windows File Objects persist in the kernel pool as long as any process has the file open. Even if an attacker deletes a file immediately after using it, if they forget to close the handle (close the Notepad window), it is recoverable. The timing of capture relative to the user's actions is the difference between finding three artefacts and finding none.
3 — Single-byte XOR is trivially broken with the script in hand
The attacker's encryption was only as strong as the secrecy of both the key and the algorithm. Storing the script in a Notepad window at time of capture gave us both. Even without the script, a single-byte XOR key can be brute-forced in 256 attempts — CyberChef's XOR Brute Force does this automatically. In real incidents, finding the encryption logic in memory is what separates a recovered plaintext from a permanently lost secret.
4 — Steganography requires the right tool and the right key — both are findable in memory
Steghide-embedded data in a JPEG is invisible to any standard file viewer. Without knowing to look for it and without the passphrase, the second flag half would be completely hidden inside an ordinary-looking image. The memory dump gave us the image file AND the decrypted first half that served as its passphrase. Neither piece alone was sufficient — the investigation required chaining them together.
5 — Multi-hop evidence chains are the norm in sophisticated attacks
No single plugin or single artefact told the complete story. pslist flagged the anomaly. cmdline identified the files. filescan found the handles. dumpfiles extracted the content. CyberChef reversed the crypto. steghide extracted the hidden payload. Each step depended on the previous one — which is exactly how attackers design their evidence trails. Real investigations always require this kind of multi-source correlation.
