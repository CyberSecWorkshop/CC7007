PART 2 — INFECTION VECTOR

⏱ ~30 min · Wireshark display filters, Follow HTTP Stream, Export Objects

You know the victim IP and the suspicious domains. Now trace the infection: find the HTTP download that delivered the Hancitor payload, follow the stream to read the full request and response, and extract and hash the downloaded file.

📦
Why HTTP is recoverable but HTTPS is not
Unencrypted traffic is a gift to the analyst

HTTP on port 80 sends the full request and response in plain text. In a PCAP you can read the domain, the URI path, every header, and the complete response body — including the actual file content. Wireshark's Export Objects function reconstructs that file directly from the reassembled TCP stream. You do not need access to the victim's disk at all.

HTTPS hides the payload behind TLS. You can see the destination IP, the port, the TLS certificate, and the byte volume — but not the content. This is why the HTTP Hancitor download in this capture is particularly valuable: it gives you the file before the attacker switched to an encrypted channel for C2.

Reading the GET list — what each line tells you
The full infection chain is visible in this one output

api.ipify.org / — a legitimate public IP-lookup service. Malware queries this as its first action to determine the victim's external IP address, which it sends to the C2 server alongside system information. Its presence alone is a strong infection indicator even before any malicious domain appears.

bor4omkin.ru /207.bin and /207s.bin — Hancitor retrieving its follow-on payloads from its own C2 domain. The .bin extension is a common evasion technique — a binary file named .bin is less likely to be blocked by a proxy filtering on file extension than a .exe. The s suffix on the second request typically indicates an HTTPS-specific configuration variant.

bor4omkin.ru /b123.exe — this is the Mars Stealer executable being downloaded. Unlike the .bin files, this one uses the .exe extension openly — by this point in the infection chain, Hancitor has already established that the host is a viable target in an Active Directory environment and proceeds with the full credential-harvesting payload.

23.227.198.207 /xp3A and /8Gfw — Cobalt Strike stager requests. These short, random-looking URIs are characteristic of Cobalt Strike's default HTTP stager profile. The victim is downloading the Cobalt Strike beacon shellcode that will run in memory.

23.227.198.207 /dpixel — repeated ~30+ times — this is the Cobalt Strike HTTP beacon in its polling loop. The URI /dpixel is a well-documented default Cobalt Strike malleable C2 profile path. Each GET to /dpixel is one beacon cycle: the implant sends a small request, receives any pending commands, then sleeps before repeating. You will measure this interval precisely in Task 3.2. The repetition here confirms sustained C2 communication throughout the capture window.

sughicent.com /blaka.php and /request — separate Hancitor C2 check-ins using a different domain. Hancitor uses multiple C2 domains simultaneously for redundancy — if one is blocked, the others continue to function. Both domains were visible in your dns_queries.txt from Task 1.3.

What to take into Task 2.2
  • Follow the stream for bor4omkin.ru /b123.exe — this is the Mars Stealer executable. It is the most forensically significant download because it is named with a .exe extension, making it the clearest malware artefact to extract in Task 2.3.
  • Note the /dpixel pattern — you will return to 23.227.198.207 in Part 3 when you measure the beacon interval from SYN timestamps. The repeated /dpixel GETs you see here are the same C2 sessions you will time.
  • Note both C2 domains — bor4omkin.ru and sughicent.com. Both appeared in your dns_queries.txt. Both are now confirmed as active C2 infrastructure in the HTTP GET list.

PART 3 — COMMAND AND CONTROL TRAFFIC

⏱ ~25 min · Wireshark, tshark

You already have the answer from Task 2.1. The /dpixel GET requests to 23.227.198.207 repeated 30+ times in your http_gets.txt — that is the Cobalt Strike HTTP beacon polling loop. In this campaign Cobalt Strike uses port 80 (HTTP), not port 443 (HTTPS). Part 3 confirms this by counting connections and measuring the interval between them.

🔁
HTTP beaconing — not all C2 uses HTTPS
Port 80 blends with legitimate web traffic and leaves full content in the PCAP

Cobalt Strike can be configured for HTTP or HTTPS C2. In this campaign it uses HTTP on port 80 with the URI path /dpixel — a well-documented default Cobalt Strike malleable C2 profile path. Using port 80 means the traffic blends with normal web browsing and is permitted outbound on virtually every corporate network. The downside for the attacker is that the full request and response content is visible in the PCAP.

A Cobalt Strike beacon wakes on a fixed schedule: GET /dpixel, receive any pending commands in the response body, close, sleep for the configured interval, repeat. The interval is consistent across every cycle with very low variance — completely unlike human browsing which produces irregular, unpredictable gaps.

  • 23.227.198.207 is second with 374 connections — this is the Cobalt Strike C2. Each of those 374 connections is one /dpixel beacon cycle: tiny bytes sent, tiny bytes received, very short duration. High count plus tiny uniform transfers = beacon.
  • The distinction matters — do not assume the top IP is the C2. Look at the session pattern: many small identical sessions = beacon. Fewer large sessions = payload delivery or data exfiltration.
  • Record 23.227.198.207 as your C2 IP — you will use it in Tasks 3.2 and 3.3.

PART 4 — FLOW ANALYSIS: CONVERSATION STATISTICS

⏱ ~20 min · tshark -z conv,tcp

Parts 1–3 analysed individual packets and streams. Part 4 looks at the traffic from a higher level: which host pairs communicated, how much data moved between them, and how many separate sessions were established. This is what NetFlow does — and tshark can produce the same data directly from the PCAP using its built-in conversation statistics feature.

📊
tshark -z conv,tcp — the PCAP's built-in flow view
Same fields as NetFlow, derived directly from the capture

The -z conv,tcp flag tells tshark to compute conversation statistics across the whole capture: for every unique pair of IP:port endpoints, it reports the address pair, total frames sent each direction, total bytes each direction, and the relative start time and duration of the conversation. These are exactly the fields in a NetFlow record — Source IP, Destination IP, ports, bytes, packets — produced from the PCAP itself without any separate collection infrastructure.

This is important for two reasons. First, it surfaces the full communication picture in one command without requiring you to read every packet. Second, it is derived from the same evidence file as everything else in this workshop — there is no fabricated data and no separate file to verify.

Why you are building this — not filling it in
The skill is construction, not completion

The Five Rules for a Defensible Timeline

Rule 1
Every row must have an evidence source
Name the specific file or tool output that supports each event. "tshark output" is not specific enough. "tshark SYN timestamps — file: syn_timestamps.txt, rows 1–5" is. If you cannot name the source, the row does not belong in the timeline.
Rule 2
Timestamps come from the PCAP — not from the scenario
Use the HTTP Date header, the relative frame timestamps from tshark, or the conversation start times from -z conv,tcp. Events that happened before the capture window (the Word document delivery) get a relative label like "T-0 (pre-capture)" — not an invented time.
Rule 3
Confidence levels must be honest
High = you have a direct timestamp or artefact from this PCAP. Medium = you are inferring ordering from logical dependency (C2 requires execution, which requires download). Low = you are citing known malware TTPs with no direct PCAP evidence. Never assign High to an inference.
Rule 4
Include Low-confidence events — but label them
Mars Stealer is documented to harvest credentials from browser stores. You did not observe this directly in the PCAP. Include it anyway — at Low confidence, sourced to threat intelligence. Omitting it leaves a remediation gap. Labelling it honestly preserves the integrity of your High-confidence rows.
Rule 5
Map every event to MITRE ATT&CK
Use the MITRE ATT&CK Enterprise matrix. Each event maps to a Tactic (the goal) and a Technique (the method). For example: Initial Access → T1566.001 Phishing. Command and Control → T1071.001 Web Protocols. Look up the correct technique IDs — do not guess.

Your Timeline Structure

Build your timeline as a table with these five columns. You can create it in any tool available to you — a text file, a spreadsheet, a Word document, or typed directly into the WebLearn discussion post.

📐 Required columns — include all five

1. Timestamp / Order — UTC time from the PCAP where available, relative label (T-0, T-1, etc.) where not.

2. Event — one sentence describing exactly what happened. Be specific: name the IP, the file, the port, the byte count.

3. Evidence Source — the specific tool output, command, or Wireshark view that supports this event. Name the output file where you saved it.

4. MITRE ATT&CK — Technique ID and name. Use the full ID (e.g., T1071.001 not T1071).

5. Confidence — High, Medium, or Low. One word. Your justification for the level goes in the Evidence Source column.

What Your Timeline Must Cover

Your timeline must account for all of the following. How you order them, what timestamps you assign, and what confidence level you apply to each is your analytical judgement.

Events to include — at minimum
  • Initial infection — the Word document delivery. This is pre-capture. What confidence level does that warrant, and why?
  • The Hancitor HTTP download — you have the URL, the filename, the byte count, and the hash. All four go in the event description. The timestamp comes from the HTTP Date header you read in Task 2.2.
  • First Cobalt Strike C2 beacon — you have the C2 IP, the TLS domain, and the beacon interval. The timestamp comes from your syn_timestamps.txt first entry.

  • Mars Stealer credential harvesting — no direct PCAP evidence of the harvesting itself. What confidence level, and what is your source?
  • Credential exfiltration — you have an IP, a port, and a byte count from Task 4.2. This is directly evidenced. What confidence level does it get?
  • Any additional findings from your own analysis that are not listed above. If you found something in the PCAP that surprised you, it goes in the timeline.

Two students running the same PCAP will get the same numbers, but the wording, confidence assignments, and ordering decisions should reflect your own reasoning. The discussion is more interesting when timelines differ slightly — that is the comparison you are being asked to make.
